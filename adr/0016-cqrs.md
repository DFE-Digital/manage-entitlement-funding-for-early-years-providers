# ADR-0016: Use CQRS to separate reads and writes

## Status

Accepted

## Context

The service will contain operations with differing business and data-authorisation rules.

We want controllers to remain focused on HTTP concerns rather than containing application or data-access logic. We also want to avoid coupling the application structure to a persistence technology.

## Decision

We will use a lightweight Command Query Responsibility Segregation (CQRS) pattern.

Application operations will be represented as either:

- **Queries**, which retrieve data without changing application state.
- **Commands**, which change application state.

Controllers will delegate application operations to command or query handlers.

Handlers will be responsible for coordinating the business and data-authorisation rules applicable to that operation.

CQRS does not imply separate read and write data stores. The persistence technology and the patterns used by handlers to access it are separate architectural decisions and will be determined and documented later.

## Consequences

- Controllers remain thin and do not contain application or persistence logic.
- Read and write operations can evolve independently.
- Data-authorisation rules can be applied to the specific operation being performed.
- Persistence choices are not constrained by this decision.
- The service will contain additional command, query and handler types.
